# Mac、手机向 Linux 发送文件失败：原因与修复

2026-11-01，修复版已由用户确认 Mac → Linux、手机 → Linux 均成功传输文件。本记录针对文件传输窗口，不涉及剪贴板复制粘贴。

## 现象与原因

| 问题 | 代码或现场证据 | 修复 |
| --- | --- | --- |
| Linux 可以主动邀请对端，但没有接收对端邀请的入口 | 文件窗口只有创建邀请、查询已创建会话的流程，没有查询待接收邀请 | 窗口打开期间查询待接收邀请；验证发送方属于关联设备，用户接受后加入对方已有会话 |
| 收到邀请后仍显示“请刷新关联设备”，刷新按钮变灰 | 启动查询没有填充设备列表；连接期间又禁止刷新 | 同一次查询自动填充关联设备；接受邀请时选中发送方，刷新后保留当前选择 |
| 对端取消后仍长时间等待 | 测试记录中对端状态为 4，窗口仍持续查询连接信息 | 对状态 1、2、4 分别按取消或拒绝结束等待，恢复空闲操作 |
| 普通直连的文件确认能力与声明不一致 | 对外声明支持 ACK，但普通 Flurry 构造参数为 0；手机专用分支已使用 1 | 普通直连也启用 ACK。该代码问题已修复，但本轮没有单独证明它就是最初发送失败的触发点 |
| 预加载 WXP2P 后缺少普通直连入口 | 后端只等待 WXP2P 调度命令，无法直接接受 server 命令 | 在同一进程内进入 TLS 监听，保留已经发布的证书；发布就绪端点，防止迟到的调度结果切换已选择的直连角色 |

## 修复范围

- `scripts/fcitx5-wetypex-account.sh.in`：新增 `pending-file-invite`，只请求关联设备和待接收邀请，返回设备列表并过滤自身或未关联发送方。
- `src/backend/business_services.hpp`：使用 GroupRequest filter 65，解析 Group field 7 的邀请；不提供 current_transfer_code，查询本身不消费邀请。
- `src/transfer/main.cpp`：自动加载设备、显示接收提示、通过 `p2p-update` 加入原会话、验证对端身份、处理取消和拒绝、抑制重复提示。
- `src/backend/macos_host.cpp`：修正 ACK 参数，并让预加载后端支持普通直连。
- 测试覆盖设备列表、接受/拒绝、原会话保持、身份不匹配、迟到调度、取消恢复以及账户工具的发送方过滤。

邀请码、证书和设备标识不进入公开报告。诊断仅使用操作结果和状态等元数据。本次未上传实际传输的文件或账户数据。

- 修复前基线：`b2bbfc87f491677b238a67b9c3417cee2c5d21e4`，正式安装为 `1:0.1.0rc3-1`。
- 文件窗口、账户工具及引擎宿主已在本机编译。三个相关 CTest 测试组通过；GUI 测试使用模拟账户和后端，不访问真实配对或网络。
- 用户明确确认 Mac → Linux 的链路和文件传输成功，随后确认手机 → Linux 也成功。测试使用临时修复版；未独立比较两端文件哈希，也未重新记录官方客户端版本。

- 接收邀请需要保持文件传输窗口打开，尚未实现关闭窗口后的常驻接收。
